# Нагрузочное тестирование SSE

## Зачем

Этот скрипт проверяет способность backend-сервера обрабатывать большое количество одновременных SSE-соединений (Server-Sent Events). Тестируются три аспекта:

1. **Устойчивость соединений** — сервер должен поддерживать сотни параллельных long-lived HTTP-соединений без падения.
2. **Доставка событий** — при создании записей в аудит-логе события должны доставляться всем подключённым клиентам.
3. **Стабильность под нагрузкой** — heartbeat'ы, reconnect и отключение клиентов не должны вызывать утечек памяти или падения сервера.

Скрипт написан на чистом Node.js без внешних зависимостей и использует `node:http` для прямого контроля над соединениями.

---

## Предварительные требования

- **Node.js 18+** (рекомендуется 20+)
- **Запущенный backend** — `npm run dev` в `apps/backend`
- **PostgreSQL доступен** — backend подключается к БД для аутентификации
- **Пользователь в БД** — учётная запись с указанным login/password (по умолчанию `admin@example.com` / `admin123`)

---

## Аутентификация

Скрипт использует JWT-аутентификацию через заголовок `Authorization: Bearer <token>`:

1. **Login** — `POST /api/auth/login` с login/password → получаем `accessToken`
2. **SSE-подключение** — `GET /api/audit-log/stream` с заголовком `Authorization: Bearer <accessToken>` → `text/event-stream`

Токен автоматически обновляется при истечении (401 от сервера).

## Запуск

### Быстрый старт

```bash
node scripts/sse-load-test.mjs --login admin@example.com --password admin123
```

Запустит дефолтные стадии (10 → 50 → 100 → 200 соединений, по 60 секунд каждая).

### Полная конфигурация

| Параметр | По умолчанию | Описание |
|----------|-------------|----------|
| `--host` | `localhost` | Хост backend-сервера |
| `--port` | `3000` | Порт backend-сервера |
| `--login` | `admin@example.com` | Email пользователя для аутентификации |
| `--password` | `admin123` | Пароль пользователя |
| `--stages` | `10:60,50:60,100:60,200:60` | Стадии нагрузки в формате `коннекты:секунды` |
| `--event-interval` | `10` | Интервал (сек) между инъекциями событий |
| `--inject-path` | `/api/projects` | Эндпоинт для инъекции событий |
| `--ssl` | отключён | Использовать HTTPS вместо HTTP |

### Примеры

**Минимальная нагрузка (10 соединений)**

```bash
node scripts/sse-load-test.mjs \
  --stages "10:60" \
  --login admin@example.com \
  --password admin123
```

**Средняя нагрузка (50 соединений)**

```bash
node scripts/sse-load-test.mjs \
  --stages "10:30,50:120" \
  --login admin@example.com \
  --password admin123
```

**Максимальная нагрузка (200 соединений)**

```bash
node scripts/sse-load-test.mjs \
  --stages "50:30,100:30,200:120" \
  --login admin@example.com \
  --password admin123
```

**Долгосрочный тест (30 минут, 50 соединений)**

```bash
node scripts/sse-load-test.mjs \
  --stages "50:1800" \
  --event-interval 30 \
  --login admin@example.com \
  --password admin123
```

**Без инъекции событий (только соединения)**

```bash
node scripts/sse-load-test.mjs \
  --stages "100:300" \
  --event-interval 0 \
  --login admin@example.com \
  --password admin123
```

## Мониторинг

### Что показывает скрипт

Каждые 5 секунд выводится таблица с текущими метриками:

| Метрика | Описание |
|---------|----------|
| Время работы | Сколько времени работает тест |
| Коннектов сейчас | Количество активных SSE-соединений |
| Коннектов всего | Сколько соединений было создано за всё время |
| Макс. параллельных | Максимальное количество одновременных соединений |
| Latency (подключение) | min/avg/max/p50/p95/p99 время установки соединения (мс) |
| Событий всего | Количество полученных SSE-событий |
| Heartbeat'ов | Количество полученных keepalive-сообщений |
| Ошибок (не-auth) | Ошибки подключения (таймауты, разрывы) |
| Ошибок (auth) | Ошибки аутентификации (401) |
| Инъекций (успех/ошибка) | Результат POST-запросов для инъекции событий |
| События по типам | Распределение событий по типам (audit-log, projects:change и т.д.) |

### Мониторинг сервера

Параллельно со скриптом рекомендуется следить за ресурсами сервера:

**RAM (процесс Node.js)**

```bash
# Через clinic.js (рекомендуется)
npx clinic doctor -- node apps/backend/dist/index.js

# Или через top/htop, PID процесса backend
```

Индикаторы:
- RSS растёт при подключении клиентов — нормально (каждое соединение = буферы)
- RSS не возвращается после отключения клиентов — утечка памяти
- Heap size превышает 512MB при < 500 соединений — проблема

**CPU**

```bash
# macOS / Linux
top -p $(pgrep -f "node.*backend")

# Или
htop -p $(pgrep -f "node.*backend")
```

Норма: CPU < 30% при 200 соединениях и инъекции событий каждые 10 секунд.

**PostgreSQL — активные соединения**

```sql
-- Активные соединения к PostgreSQL
SELECT count(*), state
FROM pg_stat_activity
WHERE datname = current_database()
GROUP BY state;

-- Длительные запросы
SELECT pid, now() - pg_stat_activity.query_start AS duration, query, state
FROM pg_stat_activity
WHERE (now() - pg_stat_activity.query_start) > interval '5 seconds'
ORDER BY duration DESC;
```

**OS-level — файловые дескрипторы**

```bash
# Linux
ls /proc/$(pgrep -f "node.*backend")/fd | wc -l

# macOS
lsof -p $(pgrep -f "node.*backend") | wc -l
```

Каждое SSE-соединение использует 1 файловый дескриптор. Лимит по умолчанию: 1024 (macOS) / 1024 (Linux).

## Красные флаги

| Метрика | Порог | Что значит |
|---------|-------|------------|
| Погрешность p95 latency | > 5000 мс | Сервер не справляется с ramp-up, соединения долго устанавливаются |
| Ошибки (не-auth) | > 5% от коннектов | Сервер разрывает соединения (OOM, таймаут, переполнение) |
| Ошибки (auth) | > 0 | Проблема с аутентификацией или истекшим токеном |
| Heartbeat'ов | < (коннекты × время / 30) | Сервер не отправляет heartbeat'ы — соединения могут быть мёртвыми |
| Событий | 0 при наличии инъекций | Инъекция событий не работает или события не доставляются |
| RAM (RSS) | Рост > 100MB за стадию | Утечка памяти на каждом новом соединении |
| CPU | > 80% | Сервер перегружен — нужно масштабировать |
| Файловые дескрипторы | > 80% от лимита | Скоро будет EMFILE — нужно увеличить ulimit |

## Сценарии тестирования

### 1. Baseline — базовая проверка

Одно соединение, 5 минут. Проверяем, что SSE работает штатно.

```bash
node scripts/sse-load-test.mjs \
  --stages "1:300" \
  --login admin@example.com \
  --password admin123
```

**Что смотрим:**
- Соединение устанавливается без ошибок
- Heartbeat приходит каждые 30 секунд
- При создании записи в аудит-логе событие доставляется клиенту
- Latency подключения < 100 мс

### 2. Ramping — плавное нарастание нагрузки

10 → 50 → 100 → 200 соединений, по 60 секунд каждая стадия.

```bash
node scripts/sse-load-test.mjs \
  --stages "10:60,50:60,100:60,200:60" \
  --login admin@example.com \
  --password admin123
```

**Что смотрим:**
- Latency подключения растёт пропорционально или нет
- Ошибок нет или < 1%
- Heartbeat'ы приходят от всех соединений
- RAM растёт линейно (не экспоненциально)

### 3. Event delivery — доставка событий

При 100 активных соединениях проверяем, что все получают события.

```bash
node scripts/sse-load-test.mjs \
  --stages "100:120" \
  --event-interval 5 \
  --login admin@example.com \
  --password admin123
```

**Что смотрим:**
- Количество событий ≈ (время / interval) × коннекты
- Все клиенты получают события (нет "замёрзших" соединений)
- Нет задержек доставки > 2 секунд

### 4. Disconnect storm — массовое отключение

Проверяем корректность массового отключения клиентов.

```bash
node scripts/sse-load-test.mjs \
  --stages "200:30,0:10" \
  --login admin@example.com \
  --password admin123
```

Примечание: стадия `0:10` отключит всех клиентов и подождёт 10 секунд.

**Что смотрим:**
- Все соединения корректно закрываются
- RAM возвращается к исходному уровню
- Нет ошибок в логах сервера

### 5. Long-running — долгосрочный тест

50 соединений на 30 минут. Проверяем стабильность.

```bash
node scripts/sse-load-test.mjs \
  --stages "50:1800" \
  --event-interval 30 \
  --login admin@example.com \
  --password admin123
```

**Что смотрим:**
- RAM стабильна (не растёт со временем)
- Heartbeat'ы не пропадают
- Все соединения остаются активными
- CPU стабильна

## Интерпретация результатов

### Норма

- **Latency подключения**: < 200 мс (p95), < 500 мс (p99)
- **Ошибки подключения**: 0 при < 200 соединений, < 1% при 200+
- **Heartbeat'ы**: приходят от всех соединений каждые ~30 секунд
- **RAM**: растёт линейно с количеством соединений (~50-200KB на соединение)
- **CPU**: < 30% при 200 соединениях

### Проблемно

- **Latency p95 > 2 секунды** — сервер медленно обрабатывает новые подключения
- **Heartbeat'ы пропадают** — сервер перегружен и не успевает отправлять keepalive
- **События не доставляются** — EventEmitter переполнен или есть проблема с фильтрацией
- **RAM растёт экспоненциально** — утечка памяти в обработчиках SSE

### Критично

- **Сервер падает при > N соединений** — нужно увеличить лимиты ОС (ulimit, fs.file-max) или оптимизировать код
- **PostgreSQL переполняется соединениями** — при высокой нагрузке нужен пул соединений
- **Файловые дескрипторы исчерпаны** — `EMFILE: too many open files`; увеличить `ulimit -n 65536`
- **Heartbeat'ы полностью пропадают** — сервер "завис" и не обрабатывает pending I/O

## Архитектура скрипта

```
┌─────────────────┐
│  parseArgs()    │  Парсинг CLI-аргументов
├─────────────────┤
│  getSession()   │  POST /api/auth/login → JWT
├─────────────────┤
│  SseClient      │  EventEmitter, подключается к /api/audit-log/stream
│  (node:http)    │  Authorization: Bearer <JWT>
│                 │  Парсит SSE: data/heartbeat/event lines
├─────────────────┤
│  Metrics        │  Сбор и форматирование метрик
├─────────────────┤
│  runLoadTest()  │  Оркестрация: ramp up → event injection → metrics
└─────────────────┘
```

### Потоки данных

1. **Аутентификация**: login → JWT (сохраняется в памяти скрипта)
2. **SSE**: GET /api/audit-log/stream + Authorization: Bearer <JWT> → text/event-stream
3. **Инъекция**: POST /api/projects + JWT → запись в БД → audit-log event → доставка клиентам
4. **Метрики**: сбор → форматирование → вывод каждые 5 секунд
