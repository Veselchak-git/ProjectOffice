# UI Kit Components

Документ фиксирует обязательные правила организации компонентов в `packages/ui-kit/src/components`.

Эти правила нужно применять при создании и изменении компонентов UI kit. Документ не заменяет общие правила FSD для frontend-приложения, но сохраняет близкую терминологию и подход к public API.

## Общие правила

- Каждый компонент должен жить в собственной папке внутри `packages/ui-kit/src/components`.
- Папка компонента должна быть самостоятельной единицей с собственным `index.ts`.
- Публичный контракт компонента должен проходить только через `index.ts`.
- Потребители не должны импортировать внутренние файлы компонента напрямую.
- Стили компонента должны следовать [правилам CSS-токенов](./css-tokens-rules.md).
- Простые компоненты не нужно раскладывать по сегментам заранее.
- Дополнительные папки создаются только при наличии кода соответствующего типа.
- Пустые сегменты создавать запрещено.
- Компоненты UI kit не должны содержать бизнес-логику приложения.

## Простая структура

Простой компонент не должен использовать функциональные сегменты `ui`, `hooks`, `context`, `model` и `lib`, если для этого нет отдельной причины:

```text
components/
  Button/
    Button.tsx - основной компонент для экспорта
    ButtonVariant.tsx - еще один компонент для экспорта
    Button.css - стили, обязательно с @layer components и component tokens
    types.ts - типы, нужные для компонента
    index.ts - точка входа
    stories/
      Button.stories.tsx - сторис для компонента
      ...
    tests/
      Button.test.tsx - тесты компонента, хука или внутренней логики
      ...
```

В корне папки простого компонента должны лежать:

- главный публичный компонент;
- дополнительные публичные компоненты того же компонентного семейства;
- стили компонента, оформленные по [правилам CSS-токенов](./css-tokens-rules.md);
- `types.ts`, если компоненту нужны публичные или общие локальные типы;
- `index.ts` как public API компонента.

Тесты всегда должны лежать в `tests/` для файлов корне папки компонента. Тестовые файлы в корне папки компонента запрещены. Если тестируются методы в подпапках, то допускается размещать папку с тестами в подпапках, к примеру lib/tests/some-helper.test.ts или hooks/some-hook.ts

Storybook-истории всегда должны лежать в `stories/`. Storybook-файлы в корне папки компонента запрещены.

## Расширенная структура

Если компонент становится сложнее, нужно использовать стандартные сегменты:

```text
components/
  Select/
    Select.tsx
    Select.css
    types.ts
    index.ts

    ui/
    hooks/
    context/
    model/
    lib/
    stories/
    tests/
```

Сегменты не являются обязательными. Каждый сегмент создается только при наличии файлов, которые должны в нем лежать.

## `ui`

`ui` должен содержать React-компоненты, которые не должны лежать в корне папки компонента.

В `ui` кладутся:

- внутренние части основного компонента;
- визуальные подкомпоненты;
- низкоуровневые UI-примитивы;
- обертки над внешними primitive-библиотеками, если они являются деталями реализации компонента.

Пример:

```text
Select/
  ui/
    SelectTrigger.tsx
    SelectContent.tsx
    SelectItem.tsx
    SelectList.tsx
```

В `ui` запрещено класть главный публичный компонент, если он является точкой входа для потребителя. Такой компонент остается в корне:

```text
Select/
  Select.tsx
```

## `hooks`

`hooks` должен содержать React-хуки компонента.

В `hooks` кладутся:

- хуки для управления локальным поведением компонента;
- хуки для работы с DOM, focus, keyboard, refs;
- хуки для controlled/uncontrolled поведения;
- хуки, которые используются только внутри этого компонента.

Пример:

```text
Select/
  hooks/
    useSelectState.ts
    useSelectKeyboard.ts
    useSelectPosition.ts
```

Если хук является частью публичного API компонента, он должен экспортироваться через `index.ts`. В остальных случаях он остается внутренней деталью компонента.

## `context`

`context` должен содержать React Context, provider и связанные consumer-хуки.

В `context` кладутся:

- `createContext`;
- provider-компоненты;
- хуки доступа к контексту;
- типы, которые нужны только контексту, если они не используются шире.

Пример:

```text
Select/
  context/
    SelectContext.tsx
    SelectProvider.tsx
    useSelectContext.ts
```

Если контекст становится частью публичного API, его экспорт должен идти через `index.ts`.

## `model`

`model` используется только для кода, который описывает отдельную модель данных или самостоятельный механизм состояния компонента.

В `model` кладутся:

- store;
- reducer;
- state machine;
- registry;
- actions/events;
- правила переходов состояния;
- типы модели, если они относятся именно к этой модели.

Пример:

```text
ContextMenu/
  model/
    contextMenuRegistry.ts
    contextMenuTypes.ts
```

`model` запрещено использовать как папку для любых хуков. Хуки должны лежать в `hooks`, если только они не являются неотделимой частью конкретной модели и не должны находиться рядом с reducer/store.

## `lib`

`lib` должен содержать утилиты компонента.

В `lib` кладутся:

- pure-функции;
- функции нормализации данных;
- функции сравнения;
- небольшие адаптеры;
- вычисления, не зависящие от React.

Пример:

```text
Select/
  lib/
    normalizeOptions.ts
    getSelectedLabel.ts
    isOptionSelected.ts
```

В `lib` запрещено класть React-компоненты, контексты и обычные хуки компонента.

## `types.ts`

`types.ts` должен использоваться для типов компонента.

В `types.ts` кладутся:

- публичные prop-типы;
- типы option/item/column/value;
- общие типы, которые используются несколькими файлами компонента.

Если типов становится слишком много и они разделяются на независимые группы, нужно создать папку `types/`. Пока такого разделения нет, нужно использовать `types.ts`.

Папку `types/` нужно создавать только при наличии минимум двух независимых групп типов, например `props.ts`, `options.ts` и `events.ts`.

## `tests`

`tests` должен содержать тесты компонента.

Все тестовые файлы компонента должны лежать в `tests/`:

```text
Button/
  tests/
    Button.test.tsx
```

Запрещено размещать тесты в корне папки компонента:

```text
Button/
  Button.test.tsx
```

Если тестов несколько, их нужно группировать внутри `tests/` по проверяемому поведению или публичному компоненту.

## `stories`

`stories` должен содержать Storybook-истории компонента.

Все Storybook-файлы компонента должны лежать в `stories/`:

```text
Button/
  stories/
    Button.stories.tsx
```

Запрещено размещать Storybook-файлы в корне папки компонента:

```text
Button/
  Button.stories.tsx
```

Если историй несколько, их нужно группировать внутри `stories/` по публичному компоненту, состоянию или проверяемому сценарию.

## Public API

Каждый компонент должен иметь `index.ts`.

`index.ts` должен экспортировать только то, что является публичным контрактом компонента:

```ts
export { Select } from "./Select";
export type { SelectOption, SelectProps } from "./types";
```

Потребителям запрещено импортировать внутренние файлы:

```ts
// Запрещено
import { SelectTrigger } from "@nms-monorepo/ui-kit/components/Select/ui/SelectTrigger";
```

Если внутренняя часть понадобилась снаружи, нужно явно решить, становится ли она частью публичного API. Если да, она экспортируется через `index.ts`. Если нет, ее использование снаружи считается нарушением границы компонента.

## Правила размещения файлов

- Главный публичный React-компонент лежит в корне папки компонента.
- CSS-файл компонента лежит в корне папки компонента, использует `@layer components` и следует [правилам CSS-токенов](./css-tokens-rules.md).
- Внутренний React-компонент лежит в `ui`.
- React-хук лежит в `hooks`.
- React Context, provider и хуки для доступа к контексту лежат в `context`.
- Store, reducer, registry или state machine лежат в `model`.
- Pure utility лежит в `lib`.
- Общие типы компонента лежат в `types.ts`.
- Тесты лежат в `tests`.
- Сторис лежат в `stories`.
- Публичные экспорты проходят через `index.ts`.

## Запрещено

- Размещать тестовые файлы в корне папки компонента.
- Размещать Storybook-файлы в корне папки компонента.
- Размещать React-компоненты в `lib`.
- Размещать React-хуки в `lib`.
- Размещать React Context, provider или хуки доступа к контексту в `lib`.
- Использовать `model` как папку для любых хуков компонента.
- Создавать пустые сегменты.
- Создавать сегменты заранее, без файлов соответствующего типа.
- Импортировать внутренние файлы компонента из потребителей.
- Экспортировать внутренние `ui`, `hooks`, `context`, `model` или `lib` без явного решения сделать их частью публичного API.
- Размещать в UI kit бизнес-логику приложения, доменные entities, пользовательские сценарии или зависимости от `apps/*`.
- Создавать отдельный компонент в папке другого компонента, если он не является частью того же компонентного семейства.

## Очень сложные компоненты

Для больших компонентов разрешены вложенные группы внутри стандартных сегментов:

```text
Table/
  Table.tsx
  Table.css
  types.ts
  index.ts

  ui/
    header/
    body/

  hooks/
    useTableSort.ts
    useTableFilters.ts

  model/
    selection/
    column-sizing/

  lib/
    getDefaultRowId.ts
    buildColumnDefs.ts

  stories/
    Table.stories.tsx

  tests/
    Table.test.tsx
```

Такая декомпозиция разрешена только когда плоские сегменты уже мешают поддержке. Для обычных компонентов нужно использовать более простую структуру.

## Связь с FSD

`packages/ui-kit` не является FSD-приложением, но использует близкие принципы:

- папка компонента похожа на slice;
- `index.ts` играет роль public API;
- внутренние сегменты разделяют ответственность;
- `ui`, `model` и `lib` сохраняют привычную терминологию;
- shared UI не должен содержать бизнес-логику приложения.

Компоненты UI kit не должны зависеть от `apps/*`, доменных entities, страниц, features или пользовательских сценариев приложения.
